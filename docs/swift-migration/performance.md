# 성능 측정 (STA-80)

Linear: STA-80, 정규화 수정 STA-82

5,000건 라이브러리에서 Library 스캔과 검색 응답을 측정했습니다. 임시 폴더에만 만들며 실제 사용자 폴더는 건드리지 않습니다.

## 다시 측정하는 방법

```sh
scripts/measure-performance.sh        # 5,000건 생성 후 release로 측정, 임시 폴더는 끝나면 삭제
scripts/measure-performance.sh 20000  # 건수 변경
```

- `scripts/generate-perf-library.py OUTPUT_DIR [COUNT]`가 같은 인자에 같은 결과를 만듭니다(고정 시드). 텍스트 90%, 이미지 10%, 한글·영문 혼합 본문(20~200단어), 앱 8종, 태그 10종, 4건 중 1건은 노트.
- 측정 테스트는 `PlopcutCore/Tests/PlopcutCoreTests/PerformanceTests.swift`입니다. `PLOPCUT_PERF_LIBRARY`가 없으면 건너뜁니다. 기본 `swift test`에는 영향이 없습니다.
- 통과 기준: 5,000건 스캔 5초 미만, 색인 검색 100 ms 미만.

## 측정 환경

Apple M2, macOS 26.6.2, release 빌드, 폴더는 막 만든 직후라 파일 캐시가 따뜻합니다. 건당 파일 3~4개(`drop.json`, `content.md` 또는 `image.png`, `note.md`). 같은 장비에서도 파일 시스템 지연 때문에 값이 크게 흔들려 아래는 범위로 적습니다.

## 결과

| 항목 | 수정 전 | 수정 후 |
| --- | --- | --- |
| 스캔 (5,000건) | 4.0~9.1 s | 0.32~0.38 s |
| 검색 색인 만들기 (스캔 뒤 1회) | 없음 | 약 75 ms (STA-82 뒤 약 120 ms) |
| 검색 "alpha" (4,190건 일치) | 119~140 ms | 2~3 ms |
| 검색 "drop-04999" (불일치) | 236~540 ms | 3 ms |
| 검색 "zzzzqq" (불일치) | 189~450 ms | 3~6 ms |
| 검색 "라이브러리" (4,171건 일치) | 138~320 ms | 2 ms |
| 태그 + 유형 + 검색 | 12~34 ms | 0.5 ms |
| 날짜 그룹 묶기 | 70~190 ms | 약 50 ms |

수정 전 값은 `LibraryFilter.apply`에 색인 없이 필드마다 `lowercased()`를 만들던 코드, 순차 스캔 코드입니다. 표의 "검색 > 불일치"는 가장 느린 경우입니다.

## 고친 병목

1. 스캔: 폴더를 하나씩 읽던 것을 `DispatchQueue.concurrentPerform`으로 병렬화했습니다. 시간은 CPU가 아니라 파일 열기·읽기 지연이었습니다(`cat`만으로도 약 2.4 s). 결과 순서는 이전과 같게 정렬합니다.
2. 검색: `SearchIndex`가 스캔 때 드롭마다 소문자 본문(UTF-8)을 한 번만 만들고, 키 입력마다 `memmem`으로 찾습니다. 편집·삭제는 해당 항목만 갱신합니다. 색인과 검색어는 같은 규칙(소문자화 후 NFC)으로 접으므로 분해형(NFD)과 완성형 한글이 서로 찾힙니다(STA-82).
3. 타임스탬프 파싱: `Calendar` 대신 고정 형식 산술을 먼저 시도하고, 맞지 않으면 이전 코드로 돌아갑니다(테스트가 두 결과를 비교).
4. `LibraryModel`: `filtered`, 날짜 그룹, 태그·앱 목록, 사이드바 개수를 뷰를 그릴 때마다 5,000건을 돌려 계산하던 것을 데이터나 필터가 바뀔 때만 계산하도록 캐시했습니다.

## 정규화 수정 (STA-82)

STA-80 색인은 소문자 UTF-8 바이트만 비교해 분해형(NFD) 한글이 완성형 검색어로 찾히지 않았습니다. 필드와 검색어를 소문자화한 뒤 NFC로 맞추도록 고쳤습니다(ASCII만 있는 문자열은 이미 NFC라 정규화를 건너뜀). 같은 장비에서 각 3회 측정, 저장 형식은 그대로입니다.

| 항목 | STA-82 전 | STA-82 후 |
| --- | --- | --- |
| 검색 색인 만들기 (스캔 뒤 1회) | 73~78 ms | 117~124 ms |
| 검색 "alpha" (4,190건 일치) | 2.3~2.5 ms | 2.3~2.6 ms |
| 검색 "drop-04999" (불일치) | 3.1~3.4 ms | 3.1~3.5 ms |
| 검색 "zzzzqq" (불일치) | 2.9~3.1 ms | 3.0~3.8 ms |
| 검색 "라이브러리" (4,171건 일치) | 1.7~2.0 ms | 1.8~2.2 ms |
| 태그 + 유형 + 검색 | 0.4 ms | 0.4~0.5 ms |

키 입력마다 드는 검색 시간은 그대로이고, 스캔 뒤 한 번 만드는 색인이 약 45 ms 늘었습니다.

## 남은 한계

- 날짜 그룹 묶기는 키 입력마다 약 50 ms(5,000건)입니다. 사용자가 체감하는 한계는 아닙니다. 건수가 수만이 되면 그룹 경계(일 시작 시각)를 한 번만 구하도록 바꿉니다.
- 목록은 SwiftUI `List`가 보이는 행만 만듭니다. 5,000행의 화면 그리기·스크롤은 사람이 앱에서 확인해야 합니다(아래 수동 확인).
- 앱 시작 시간(프로세스 시작부터 첫 목록까지)은 UI를 포함해 자동 측정하지 못했습니다. 스캔은 백그라운드 `Task`에서 돌고 그동안 `loadingDrops`가 보입니다.

## 수동 확인 (사람이 해야 함)

1. `python3 scripts/generate-perf-library.py /tmp/nd-perf`로 만든 뒤 `PLOPCUT_STORAGE_FOLDER=/tmp/nd-perf PLOPCUT_SETTINGS_FILE=/tmp/nd-perf-settings.json`로 앱을 실행하고, 시작부터 목록이 보일 때까지 걸리는 시간을 잰다.
2. 검색창에 빠르게 입력해 입력이 끊기지 않는지, 목록을 끝까지 스크롤해 끊김이 없는지 확인한다.
3. 끝나면 `/tmp/nd-perf`를 지운다.
